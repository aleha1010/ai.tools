# Pipeline разработки с мульти-агентным ревью

Этот процесс описывает полный цикл от идеи до production-кода. Каждый этап завершается ревью, и без вердикта APPROVED переход к следующему этапу невозможен.

## Общая схема

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│   Этап 1     │    │   Этап 2     │    │   Этап 3     │    │   Этап 4     │    │   Этап 5     │
│  Domain      │───►│  PRD         │───►│  Issues      │───►│  TDD         │───►│  Code        │
│  Modeling    │    │  Synthesis   │    │  (to-issues) │    │  (implement) │    │  Review      │
│              │    │              │    │              │    │              │    │              │
│  Результат:  │    │  Результат:  │    │  Результат:  │    │  Результат:  │    │  Результат:  │
│  CONTEXT.md  │    │  PRD.md      │    │  issues на   │    │  код + тесты   │    │  финальный   │
│  + ADR       │    │              │    │  трекере     │    │               │    │  коммит      │
└──────┬───────┘    └──────┬───────┘    └──────┬───────┘    └──────┬───────┘    └──────┬───────┘
       │                   │                   │                   │                   │
       ▼                   ▼                   ▼                   ▼                   ▼
  ┌──────────┐       ┌──────────┐        ┌──────────┐        ┌──────────┐        ┌──────────┐
  │ РЕВЬЮ #1 │       │ РЕВЬЮ #2 │        │ РЕВЬЮ #3 │        │ РЕВЬЮ #4 │        │ РЕВЬЮ #5 │
  └──────────┘       └──────────┘        └──────────┘        └──────────┘        └──────────┘
```

**Ключевое правило:** каждый этап заканчивается ревью. Без APPROVED на ревью — переход к следующему этапу невозможен.

---

## Этап 1: Domain Modeling

Доменное моделирование — уточнение терминов, границ системы, сценариев для обеспечения единого языка (Ubiquitous Language).

**Вход:** запрос пользователя / задача
**Выход:** `CONTEXT.md` (глоссарий) + опционально ADR
**Скилл:** `domain-modeling`

### Ревью этапа 1

| Агент | Что проверяет | Почему именно он |
|-------|---------------|------------------|
| **review-analyst** | Корректность терминов, полнота определений, нет ли двусмысленностей | Аналитик — владелец терминологии и требований |

**Критерии APPROVED:** нет HIGH находок. HIGH = термин может привести к неправильной реализации (например, перепутаны понятия "заявка UMP" и "сделка ПАКТ").

---

## Этап 2: PRD Synthesis

Синтез Product Requirements Document — фиксация problem statement, решения, user stories, архитектурных и тестовых решений.

**Вход:** `CONTEXT.md` + устная договорённость
**Выход:** `PRD.md`
**Скилл:** `to-prd`

### Ревью этапа 2

| Агент | Что проверяет | Почему именно он |
|-------|---------------|------------------|
| **review-analyst** | Полнота user stories, соответствие бизнес-целям, edge cases | Аналитик проверяет, что PRD покрывает все сценарии |
| **review-architect-backend** | Архитектурные решения: выбраны ли правильные паттерны, слои, контракты | Архитектор проверяет, что подход не противоречит архитектуре проекта |
| **review-architect-frontend** | Архитектурные решения для UI: компоненты, стейт-менеджмент, API-взаимодействие | Фронтенд-архитектор проверяет frontend-составляющую |
| **review-security** | Есть ли риски безопасности на уровне требований (хардкод credentials, открытые эндпоинты, утечка данных) | Безопасность должна быть заложена на уровне архитектуры |

**Автовыбор:** если задача только backend — `review-architect-frontend` исключается. Если только frontend — `review-architect-backend` исключается. Если и то, и другое — оба.

**Критерии APPROVED:** нет HIGH находок ни у одного агента. Если хотя бы один REJECTED — этап не пройден.

---

## Этап 3: Issues (декомпозиция)

Декомпозиция PRD на независимые вертикальные срезы (tracer bullets) для параллельной или последовательной реализации.

**Вход:** `PRD.md`
**Выход:** issues на issue tracker'е (JIRA/GitHub)
**Скилл:** `to-issues`

### Ревью этапа 3

| Агент | Что проверяет | Почему именно он |
|-------|---------------|------------------|
| **review-analyst** | Полнота декомпозиции — все user stories из PRD покрыты issues | Чтобы не потерять функциональность при нарезке |
| **review-architect-backend** | Вертикальные срезы корректны — нет задач, которые зависят от нереализованного | Независимость issues, правильная последовательность |
| **review-architect-frontend** (если задача с UI) | Фронтенд-issues выделены корректно, нет скрытых зависимостей от бэкенда | Правильная стыковка frontend- и backend-задач |

**Критерии APPROVED:** нет HIGH находок. HIGH = потерянная функциональность или циклическая зависимость между issues.

---

## Этап 4: TDD Implementation

Реализация одной issue через Test-Driven Development с ревью после каждой итерации.

**Вход:** одна issue
**Выход:** код + тесты
**Скилл:** `tdd` (внутри `/implement`)

Запускаются 5 параллельных ревьюеров (как реализовано в task-loop v2.0):

| Агент | Что проверяет |
|-------|---------------|
| **review-architect-backend** | DI-паттерны, разделение слоёв, зависимости, избыточная сложность |
| **review-architect-frontend** (если задача с UI) | Компоненты, состояние, хуки, производительность рендера |
| **review-security** | OWASP Top 10, хардкод, инъекции, чувствительные данные |
| **review-performance** | N+1, асинхронность, кэширование, утечки памяти |
| **review-tester** | AAA pattern, покрытие, моки, assertions, flakiness |
| **review-analyst** | Соответствие бизнес-требованиям, полнота acceptance criteria |
| **review-dba** (если задача затрагивает БД) | ORM, миграции, индексы, транзакции |

**Автовыбор:**
- Всегда: `architect-backend`, `security`, `performance`, `tester`, `analyst`
- Если есть UI: `architect-frontend`
- Если есть БД: `dba`

**Критерии APPROVED:** все активные агенты APPROVED или CONDITIONALLY_APPROVED. Если хотя бы один REJECTED — код возвращается на доработку.

---

## Этап 5: Code Review (финальный)

Финальная проверка всего решения перед коммитом. Двухосевое ревью: проверка coding standards + верность спецификации.

**Вход:** завершённый код всех issues
**Выход:** финальный коммит / PR

**Скилл:** `code-review`

| Ось | Агент | Что проверяет |
|-----|-------|---------------|
| **Standards** | `code-review` (standards-ось) | Coding standards + Fowler code smells: длинные методы, большие классы, duplicate code, god objects |
| **Spec** | `code-review` (spec-ось) | Верность исходному PRD/issues — вся ли функциональность реализована, нет ли лишнего |

## Правила коммита

### Коммит разрешён только если:
- Все пройденные этапы имеют **APPROVED** на своих ревью
- Нет REJECTED на любом пройденном этапе

### При CONDITIONALLY_APPROVED:
- Коммит разрешён
- В тело коммита добавляется секция `Known Issues`

### При REJECTED:
- Коммит НЕ разрешён
- Проблемы должны быть исправлены до следующего ревью
- После исправления — повторное ревью на том же этапе

---

## Вердикты и их значение

| Вердикт | Значение | Действие |
|---------|----------|----------|
| **APPROVED** | Нет блокирующих проблем | Переход к следующему этапу |
| **CONDITIONALLY_APPROVED** | Есть MEDIUM проблемы, но они не блокируют | Переход разрешён с секцией Known Issues |
| **REJECTED** | Есть HIGH проблемы, блокирующие переход | Немедленная доработка + повторное ревью |

## Формат вывода JSON для всех агентов-ревьюеров

Все review-агенты возвращают результат в едином JSON-формате:

```json
{
  "verdict": "APPROVED | CONDITIONALLY_APPROVED | REJECTED",
  "findings": [
    {
      "severity": "HIGH|MEDIUM|LOW",
      "section": "Секция из чеклиста скилла",
      "line_start": 1,
      "line_end": 10,
      "problem": "Описание проблемы",
      "suggestion": "Конкретное исправление"
    }
  ],
  "note": "Необязательное сообщение"
}
```
